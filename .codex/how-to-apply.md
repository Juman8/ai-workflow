# AI駆動開発 導入・展開ガイド（Change Management）

> 会社にAI駆動開発を適用するためのChange Managementガイドです。
> 技術導入より**人とプロセスの変革**が成功の9割を占めます。

---

## 展開フェーズ全体像

```
Phase 0        Phase 1         Phase 2          Phase 3          Phase 4
準備・設計  →  パイロット  →  横展開準備  →  全社展開  →  定着・改善
(1-2ヶ月)     (1-3ヶ月)      (1-2ヶ月)       (3-6ヶ月)    (継続)
```

---

## Phase 0: 準備・設計

### スポンサーシップの確保

最初にやるべきことは**経営層のコミットメント取得**です。

- "AIツール代を払うだけ"ではなく、「開発文化を変える投資」として位置づける
- KPIを経営目標に紐づける（開発速度 → TTM短縮 → 競争優位）

### 変革抵抗の先読み

| 抵抗パターン | 典型的な声 | 対処 |
|------------|----------|------|
| 役割不安 | 「AIに仕事を奪われるのでは」 | "AIはペア相手、あなたが意思決定者" と明確化 |
| 品質不安 | 「AIが書いたコードは信用できない」 | レビュープロセスを強化することで品質が上がると示す |
| 学習コスト不安 | 「また新しいツールを覚えるの」 | CLAUDE.md/PRP で**AIが合わせる**仕組みを見せる |
| セキュリティ懸念 | 「コードが外部に漏れるのでは」 | .claudeignore・Enterprise契約・データポリシーを説明 |

## Phase 1: パイロット（最重要）

### チーム選定基準

```
理想的なパイロットチーム：
  ✅ モチベーションが高い（強制はNG）
  ✅ 新機能開発がある（保守メインは効果が出にくい）
  ✅ 技術リーダーが変革に前向き
  ✅ 3〜5名規模（大きすぎず、小さすぎず）
  ❌ 炎上中プロジェクト（失敗リスクが高い）
  ❌ 懐疑的なメンバーだけのチーム
```

### パイロットで測定すること

`tpl/ai-metrics.md` のベースライン計測を**必ずやる**。
数字がないと「なんとなくよかった」で終わり、横展開の根拠が作れません。

| 指標 | なぜ重要か |
|------|----------|
| タスク完了時間（SP/人日） | 速度改善の根拠 |
| コードレビュー指摘数 | 品質変化の可視化 |
| AI起因バグ数 | リスクの定量化（反対派への答え） |
| 開発者満足度（1-5） | "生産性は上がったが疲弊した"を検知 |

### 失敗パターンと回避策

| 失敗パターン | 何が起きるか |
|------------|------------|
| CLAUDE.mdなしで使わせる | AIが暴走 → 「やっぱり使えない」になる |
| ツール導入だけで教育なし | 各自がバラバラな使い方 → 効果が出ない |
| 目標なしに「自由に使って」 | 使わない人が続出 |

---

## Phase 2: 横展開準備

### 「伝道師（Champion）」の育成

パイロットチームから**2〜3名のChampion**を選出し、社内講師にします。

```
Champion の役割：
  - 他チームへのハンズオン実施
  - CLAUDE.md / PRP テンプレートのプロジェクト適用支援
  - 社内Slackチャンネルで質問対応
  - 成功事例・失敗事例の収集と共有
```

> 外部研修より**同僚からの伝播**の方が定着率が圧倒的に高いです。

### ナレッジベースの整備

横展開前に以下を準備します（このdocsリポジトリがその役割を担います）：

- [ ] 社内向けCLAUDE.mdのひな形（技術スタック固定版）を作成
- [ ] パイロットで有効だったPRPパターンを `docs/prp/` に蓄積
- [ ] AIを使った「前後比較」のビフォーアフター事例を文書化

---

## Phase 3: 全社展開

### 段階的ロールアウト戦略

```
Wave 1（月1-2）: パイロット + 希望チーム
Wave 2（月3-4）: 全開発チーム（強制ではなく"デフォルト"に）
Wave 3（月5-6）: QA・インフラ・ドキュメント担当へ拡張
```

### トレーニング設計

| 対象 | 内容 | 形式 |
|------|------|------|
| 全開発者 | CLAUDE.md/PRP の書き方、基本的な使い方 | ハンズオン 3時間 |
| テックリード | SubAgent活用、品質管理、metrics計測 | ワークショップ 半日 |
| マネージャー | KPI読み方、リスク対応、予算計画 | 説明会 1時間 |
| 経営層 | ROI報告の見方、競合動向 | エグゼクティブサマリー |

### 「強制しない・でも使いやすくする」設計

- CI/CDにClaude Codeのレビューを**オプション**で組み込む
- CLAUDE.mdを**リポジトリに最初から置く**（使わない選択肢を減らす）
- Sprint Retrospectiveに`tpl/retrospective.md`のAI振り返りセクションを**標準化**する

---

## Phase 4: 定着・改善サイクル

### 継続的改善の仕組み

```
毎Sprint:
  retrospective.md の AI活用振り返りセクションを記入
        ↓
毎月:
  ai-metrics.md で効果測定 → マネージャーに報告
        ↓
四半期:
  Champion が集まりナレッジ共有会
  CLAUDE.md/PRPテンプレートをアップデート
        ↓
半年:
  ROI計測 → 経営報告 → 次年度予算に反映
```

---

## よくある失敗と対策

| 失敗 | 原因 | 対策 |
|------|------|------|
| 数ヶ月後に誰も使っていない | 強制導入・効果の見えなさ | Champion制度 + metrics可視化 |
| チームによって使い方がバラバラ | テンプレート不在 | CLAUDE.md/PRP を会社標準として整備 |
| AIのバグで炎上 → 禁止令 | レビュープロセスなし | `tpl/bug-tracker.md` でAI起因バグを追跡・対策 |
| 「上から言われたから使う」 | トップダウン強制 | ボトムアップの成功事例を先に作る |

---

## 最初の一手：アクションプラン

> 「全社一斉導入」より「小さく勝って、数字で語って、広げる」が変革成功の鉄則です。

| タイミング | アクション |
|----------|----------|
| 今週 | 技術リーダー1人を巻き込み、CLAUDE.mdをプロジェクト1つに試験導入 |
| 来月 | そのチームで `tpl/ai-metrics.md` のベースラインを計測 |
| 2ヶ月後 | 結果をもって経営層への「パイロット結果報告会」を実施 |
| 3ヶ月後 | その数字を持って横展開予算を取る |
