## 4. AI生成コード特有のテスト観点

> AIが生成したコードは人間が書いたコードと異なるリスクを持つ場合がある。以下の観点を必ず確認する。

| 観点 | チェック内容 | 対応するテスト種別 |
|------|------------|----------------|
| 境界値・エッジケース | AIが見落としがちな空文字・null・最大値・最小値を網羅しているか | 単体テスト |
| 入力バリデーション | ユーザー入力のサニタイズ・バリデーションが適切か（SQLi・XSS） | 単体テスト・セキュリティテスト |
| エラーハンドリング | 想定外のAPIレスポンス・DB例外が適切に処理されているか | 統合テスト |
| 型安全性 | TypeScript の型チェックが通過しているか、`any` 型が混入していないか | ビルド・静的解析 |
| ハードコード | 環境依存の値（URLやID）がハードコードされていないか | コードレビュー |
| 既存コードとの整合性 | 既存コンポーネント・フックを正しく流用しているか（独自実装の重複がないか） | コードレビュー・統合テスト |
| パフォーマンス | N+1クエリや不必要な再レンダリングが発生していないか | 統合テスト・負荷テスト |
| セキュリティ | 認証・認可のバイパスがないか（AIが実装を省略するケースがある） | セキュリティテスト |

## 5. テストデータ方針

| 項目 | 方針 |
|------|------|
| 個人情報 | 実データを使用しない。ダミーデータ（faker.js等）を使用する |
| 境界値データ | 最大文字数・最小値・0件・上限件数 のデータを必ず用意する |
| 異常データ | SQLインジェクション文字列・スクリプトタグを含むデータでバリデーションテストを行う |
| 本番データの利用 | 禁止（マスキング・匿名化なしの本番データはテスト環境に持ち込まない） |

## 7. 合否基準

| 項目 | 合格基準 |
|------|---------|
| 単体テストカバレッジ | 80% 以上 |
| E2E テスト | 全ケース PASS |
| 重大バグ（P1） | 0件 |
| 高バグ（P2） | 0件（または対応方針合意済み） |

## 8. バグ優先度定義

| 優先度 | 定義 | 対応期限 |
|--------|------|---------|
| P1（重大） | システム停止・データ損失・セキュリティ脆弱性 | 即日 |
| P2（高） | 主要機能が使えない | 翌営業日 |
| P3（中） | 機能の一部が使えない・回避策あり | 今スプリント内 |
| P4（低） | 軽微な表示崩れ・文言ミス | 次スプリント以降 |
